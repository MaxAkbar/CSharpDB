Data Modeler user guide

Build and Use a Data Model

Choose the tables you want to understand, arrange their relationships, and save a readable diagram. When you need to change the database, stage supported edits in Details, review their SQL, and apply them deliberately.

1. Know what changes the database

A diagram is a saved view of part of your schema, not a separate database. The toolbar reports diagram saving status and the number of pending database changes separately.

ActionWhat changes
Add sources, move tables, group, adjust connectors, or change detail levelDiagram membership and appearance only. No schema SQL runs.
Remove a table from the canvasRemoves its card and visible connectors, not the database table.
UngroupRemoves the frame and membership, leaving tables and connectors in place.
Save / Save AsStores the diagram, including pending edits. Does not apply them.
Delete diagramDeletes the saved diagram record, not the modeled tables.
Stage changeAdds an unapplied database operation to the pending list.
Apply reviewed changesExecutes the reviewed schema SQL against the active database route.
For layout-only work: you do not need Review Changes or Apply. Saving your diagram is enough.

2. Open and build a first diagram

  1. Open your database. In Object Explorer, choose Tools → Data Model. Alternatively, right-click a table and choose Show in Data Model to start with that table and its immediate relationships.
  2. For a sharded connection, set the Route keyspace and route key, then use the checkmark to resolve the route. Confirm the displayed shard before continuing. Diagrams and schema changes belong to that route, not to every shard.
  3. The global workspace loads its saved Default Diagram if one exists. Otherwise it starts empty. Open Sources and search by table name.
  4. Choose Add for only that source, or its Add with related tables icon for the source plus its immediate incoming and outgoing foreign-key neighbors. This is one hop, not the entire connected schema.
  5. Choose Keys First to keep cards compact. Drag table headers into a useful arrangement, or choose Auto Arrange, then Fit Model.
  6. Enter a descriptive diagram name, such as Order fulfillment, and choose Save As to create a separate copy. Wait for the saved status. Use Load to reopen that named diagram later.

For example, start with an orders table and its direct relationships, then add shipment or product tables only when you need them. Choose Load All for a complete overview; it adds missing sources without moving cards already on the canvas.

Only tables and external tables are canvas nodes. Views, triggers, and other objects remain in their existing tools or appear as known dependencies in Details.

3. Select, deselect, and find tables

  • Select one table: click its card. It, its direct neighbors, and relevant relationships stay prominent; unrelated elements dim. Open Details to inspect it.
  • Select several: Ctrl-click on Windows, Cmd-click on macOS, or Shift-click to toggle individual tables. Multiple selection shows grouping controls instead of single-table schema controls.
  • Deselect: click an empty part of the canvas without dragging, or press Escape while the canvas has focus. During an active move, Escape first cancels that move.
  • Find a visible table: type into Locate table…, then choose a match. This navigates to an existing card; use Sources to add a table that is not yet visible.
  • Explore neighbors: select a table and use Show Direct Relationships. In Details, Known relationships also lists incoming and outgoing relationships outside the canvas; selecting one adds missing endpoint cards.

Select a connector to inspect its constraint and ordered column mappings. Its participating columns are highlighted. Relationship details also let you locate either endpoint.

4. Read table cards and relationships

Cards show column types and indicators for primary keys, foreign keys, uniqueness, indexes, nullability, and rowversion. For complete definitions, select one table and open Columns and declared properties or Keys, checks, and indexes in Details. Declared types include length, precision, and scale; properties include defaults, collation, and identity.

Primary/unique constraints, checks, and indexes are distinct objects. An engine-maintained supporting index is read-only: change its owning constraint instead. External tables and archive relationships can be arranged but cannot be schema-edited here.

Crow's-foot legend

The parent is the referenced table; the child contains the foreign key. Automatic layout generally places parents to the left of children, but moving a card does not change the relationship's meaning.

MarkerMeaningWhen shown
|| — exactly oneA child row requires one parent.Parent end when all participating child columns are required.
○| — zero or oneThe reference is optional, or there is at most one matching child.Parent end when a child FK column is nullable; child end when the complete FK column set has a matching primary/unique key or unique index.
○< — zero or manyA parent may have no children or several.Child end when the complete FK column set is not uniquely constrained. An ordinary index does not make it unique.

Solid lines are physical foreign keys, dotted lines are draft relationships, and dashed lines are archive relationships. Names and mappings appear on hover or selection to avoid permanent label clutter.

A composite foreign key has one connector per constraint, not one unrelated line per column. Selection highlights all participating columns; Details shows their ordered mappings. A column's membership in a composite primary key does not make that column individually unique.

5. Arrange and navigate the canvas

ControlHow to use it
Move a tableDrag its header, away from the detail and remove buttons. Release to finish the move. Dragging a grouped table moves only that table.
Auto ArrangeRepositions visible tables and groups into a repeatable relationship-aware layout. Groups remain intact. Custom bend guides are retained; bends internal to a moved group translate with it.
Tidy ModelSwitches to Keys First, resets custom routes, arranges, and fits the model. Confirms before discarding custom routes. Keeps each group's internal table arrangement.
Fit ModelCenters and scales the model without changing table positions. Use it to recover an off-screen diagram.
Keys FirstShows primary keys, foreign keys, and visible relationship-endpoint columns. This is the default for newly added cards.
Expand All / Collapse AllUse the toolbar icons to show every column or only headers. A card's own detail button cycles its visibility independently.
Pan and zoomDrag empty background to pan. Use the wheel to zoom around the pointer, or the zoom controls. Reset returns zoom to 100%.
RefreshUpdates metadata and the schema baseline, preserving current positions, groups, routes, and pending intent. It does not reload an older saved layout or globally rearrange cards.

New sources are placed around existing content without moving it. Disconnected components are separated during arrangement; unrelated tables get their own lane in a full model. Cycles cannot all point left-to-right, so those tables are arranged together.

Existing diagrams retain their saved detail visibility. Hide Sources or Details when you want more unobstructed canvas space.

6. Group tables into named areas

  1. Ctrl/Cmd-click or Shift-click at least two tables, then choose Group Selected.
  2. In Details, enter a Group name and choose Rename Group. Choose a palette color. The frame fits the members automatically without moving them.
  3. Drag the group's title to move every member together. Drag an individual table header to change its position within the group; the frame follows.
  4. To change membership, select the relevant tables, choose a Target group, and use Add/Move Selected Tables Here. Each table belongs to at most one group.
  5. Use Remove from Group to detach a member, or select the group and choose Ungroup to remove its frame. Neither action drops database tables.

Membership is explicit: dragging across a boundary does not add or remove a table. Single-table groups remain; empty groups are pruned. Groups may include physical, draft, and external tables. There are no nested, collapsed, or manually resized groups.

Group movement translates custom bends only when both endpoints are members. Bends on connections to outside tables stay fixed while their endpoint legs follow the moved cards. New sources avoid occupied group bounds. Manual overlaps are allowed but produce warnings; Auto Arrange can separate groups and ungrouped tables.

7. Adjust connector bends

  1. Select a relationship line to reveal its bend handles and segment grips.
  2. Drag a bend to move its routing guide. Drag a segment grip sideways to make a right-angle detour. Double-click a segment to add a bend at that point.
  3. For explicit controls, open Details → Connector route. Add Bend creates and focuses a guide on the longest segment. Remove Bend removes the selected guide.
  4. Release to finish and save the adjustment on a saved diagram. Press Escape during a move to cancel it. Use Reset to Automatic to discard the route guides; removing the last bend also restores automatic routing.

Moving a single table keeps its saved guides fixed while the endpoint legs follow the column rows. Collapsed cards use separate header-side attachment lanes. If a table obstructs a saved guide, the canvas temporarily shows a safe automatic route and a warning. The guide is retained: move the table away, reposition the guide, or reset the route.

Connector editing changes appearance only. It does not add, remove, or modify a foreign key. To change the actual relationship, use the schema inspector and review the staged SQL.

8. Save, reopen, and undo

Named diagrams save completed table/group moves, connector adjustments, and explicit layout/detail commands. Pan and zoom saving is debounced briefly. A new global Default Diagram begins saving after a change; merely opening an untouched empty workspace does not create a record. For an unnamed table-context diagram, enter a name and choose Save first.

  • Save: stores the current diagram under the name entered. Check the status for saving, saved, or save-failed feedback before closing.
  • Save As: enter a new, unused name, then choose Save As. It creates a copy and refuses to overwrite an existing named diagram.
  • Load: choose the saved name in the same database and route. Loading restores its positions, groups, connector bends and attachment sides, detail levels, viewport, and pending changes.
  • Undo / Redo: use the toolbar to reverse or restore diagram edits and unapplied schema edits. A completed drag is one history action. History is session-local and resets after refresh, diagram load, or successful schema application.

Save an unnamed diagram before switching routes or loading another one. Undo does not reverse committed database changes, and its history is not restored when you reopen a saved diagram.

Diagrams are stored as JSON in the database-local __data_model_diagrams backing table. Current version-5 records retain the layout and pending intent; earlier versions are migrated on load. Use System Catalog → sys.diagrams to inspect saved diagrams, or Internal Storage to see the backing-table inventory. Do not edit backing records directly.

9. Stage supported schema edits

Select exactly one writable table, open Details → Stage schema change, choose the change type, fill in its fields, and choose Stage change. The inspector previews pending edits in order. This does not execute SQL.

Example: add a column and index it

  1. On an existing writable table, choose Add Column. Use an unused name such as caption, declared type VARCHAR(60), and optional literal default 'new'. Stage the change.
  2. Choose Create Index. Enter an unused index name and select caption in the ordered column picker. Stage this second change.
  3. Inspect both pending operations. If you rename the new column before creating the index, use its new preview name in later operations.
  4. Continue with validation and review. Saving the diagram alone leaves both edits unapplied.

Tables, columns, checks, and indexes

New Table creates a draft. Add its initial columns before staging other edits on it so they can be included in CREATE TABLE. For a composite primary key, clear Primary key on the initial column, add the remaining columns, and then stage an ordered primary-key constraint.

The inspector supports table/column rename and drop, supported type facets, nullability, literal defaults, collation, primary/unique keys, checks, foreign keys, and ordinary/unique indexes. Use Stage removal beside an existing supported constraint or user-managed index to remove it through review.

  • Defaults are literal values, including supported typed literals or NULL, not arbitrary function expressions.
  • ROWVERSION can be declared during initial draft-table creation, not added to an existing table. Add it before other edits turn subsequent draft column additions into ALTER operations.
  • A new column can have a named column CHECK. For an existing column, add a named table CHECK with a row-local SQL expression referring to it; there is no ALTER operation to attach a column-scoped CHECK.
  • Index pickers retain column order and optional collations. ASC/DESC index direction options are not supported. Engine-maintained supporting indexes cannot be edited independently.

Controls share validation with Table Designer. Unsupported combinations are blocked with an explanation; the modeler does not silently rebuild tables to simulate unavailable engine features.

Composite keys and foreign keys

  1. Stage the referenced primary/unique key first if it does not exist. In the ordered picker, add each key column and use the move-up controls to put them in the intended order.
  2. Select the child table and choose Add Foreign Key. Enter the constraint name and choose its child columns.
  3. Choose Referenced table and the same number of Parent columns (matching order). Each position is one mapping, for example:
PositionChild: ordersParent: customers
1tenant_idtenant_id
2customer_idid

Choose supported On delete and On update actions. RESTRICT, NO ACTION, CASCADE, SET NULL, and SET DEFAULT are subject to column and engine restrictions. To replace an existing FK, choose it under Relationship to replace; otherwise leave Create new relationship. Stage the change and review the resulting statements.

Later operations depend on earlier staged names and definitions. If you remove an earlier pending change, inspect and correct later dependent operations before applying.

10. Validate, review, and apply safely

  1. Inspect the pending list and dependencies. Known view and trigger dependencies help assess destructive changes but are not guaranteed exhaustive. Check external consumers before dropping or renaming objects.
  2. Optionally choose Check existing data. It explicitly checks relevant NULLs, duplicate candidate keys with their collations, and orphaned foreign keys. It can scan related tables outside the canvas. Use Cancel to stop remaining work.
  3. Choose Review Changes. Read the exact SQL, affected tables, validation errors, warnings, and destructive-change labels. Correct errors before proceeding. Changes to the pending list require a new review.
  4. Choose Apply reviewed changes only when ready. The modeler verifies the live schema baseline, then applies the reviewed batch, including native foreign-key DDL, in one transaction on the current database route.
  5. Read the result. On success the schema baseline updates and applied intent is cleared. Confirm the separate diagram-save status before closing.

Data checks are opt-in and may be expensive; opening or reviewing a diagram does not run them. New or converted columns that cannot be checked against live data are reported as skipped, not as passing. The engine still validates constraints during Apply; a prior successful check is not a guarantee that data has remained unchanged.

ResultWhat to do
Schema changed outside the modelerThe stale plan is blocked. Refresh, inspect how pending intent fits the new baseline, and review again. It is not silently replayed.
A statement failsThe transaction is rolled back and pending changes remain. Correct the cause, then review again before retrying.
Client lacks transactional review supportApply is unavailable. Do not assume the modeler will apply a partially committed sequence; use a connection that supports the required transaction behavior.
Schema applied, but diagram save failedThe database commit succeeded. Do not reapply the old SQL. Refresh to reconcile the schema, inspect the diagram, and retry saving it.

11. Export and open related tools

  • Export SVG / Export PNG: downloads the current model as an image without changing layout or executing SQL. Large PNGs are scaled down; SVG is useful when you need scalable output.
  • Export pending SQL: reviews the pending plan and exports its transaction script without executing it. Inspect it before running it anywhere; an exported file is not a live schema-drift check.
  • Open in Query Designer: takes the model into the existing query-building workflow.
  • Table data, Data Hygiene, System Catalog, and Compare / Deploy: use the contextual actions for records, deeper data-quality work, catalog inspection, or schema comparison. These remain separate tools.

13. Troubleshooting

SymptomTry this
Most tables look dark or dimmedA table, group, or relationship is selected. Click empty canvas or focus the canvas and press Escape.
I cannot move a tableDrag the table header rather than a connector, column, or header button. Drag the group title only when you want to move all members.
The diagram is crowded or off-screenUse Keys First and Fit Model first. Auto Arrange repositions content; Tidy Model also resets custom routes. Prefer a smaller source selection for detailed work.
A foreign-key line is missingBoth endpoint cards must be visible. Use Known relationships or Show Direct Relationships to add the missing endpoint. Check metadata warnings for a source that no longer exists.
A saved bend is not being followedA card may obstruct it. Move the card away, adjust the bend, or Reset to Automatic. The fallback does not erase the saved guide.
Schema editing controls are missingSelect one writable physical or draft table, not a group, multiple tables, or an external table. Open Details.
My saved arrangement is missingCheck the database, route, and diagram name. Use Load to open the named diagram; the global entry loads Default Diagram. Look for a save-failed message.
A table disappeared after refresh or loadRead missing-source warnings and verify live metadata. Removed sources cannot keep active group membership; other saved positions are retained.
Changes are saved but the database is unchangedDiagram saving preserves pending intent. Database changes require Review Changes and Apply reviewed changes.
